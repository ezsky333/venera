# Venera NAS 服务端 — 需求分析与技术方案（决策版）

> 配套文档：[01-架构分析.md](./01-架构分析.md)（代码级细节与源码位置）

---

## 一、这份文档回答什么

你的需求有 4 个能力点：

1. NAS 服务端上线后，App **自动同步**账号配置、收藏等到 NAS；
2. 服务端**自动下载**收藏夹全部内容；
3. App 阅读时，若 NAS 已缓存，**优先从 NAS 读**；
4. App 里有按钮能**主动触发下载到 NAS**。

我做完了两个仓库的代码分析，并对最不确定的技术点（JS 漫画源能否脱离 Flutter 跑）做了**实测验证**。下面是结论与可选项，供你决策。

---

## 二、核心结论（三个"已确认"和一个"已破解"）

### ✅ 结论 1：漫画源可以在服务端跑，不需要 Flutter

我把 `venera/assets/init.js`（JS 桥，40 KB）与 `venera-configs` 的 35 个源脚本，原样喂给 Go 的 `goja` 引擎：

```
init.js 加载 .............. OK
35 个源脚本解析 ............ OK=35  FAIL=0
ES6+ 语法 .................. async/await、?.、??、class fields、
                             generator、for-of 解构、命名分组正则 全部通过
MangaDex 端到端 ............ loadInfo 返回真实标题「我独自升级」 ✅
```

源只需要宿主提供 **12 个左右的 host API**（`Network.get/post/delete`、`Convert.*`、`HtmlDocument`、`cookie`、`delay`、`load_data/save_data`、`getLocale`），其余（`UI.*` 弹窗类）可以直接 stub 成空操作。**这是一个可控的工程量，不是无底洞。**

### ✅ 结论 2：现有 WebDAV 同步机制可以直接复用

`lib/utils/data_sync.dart` 就是一个 WebDAV 客户端：把 `history.db` + `local_favorite.db` + `appdata.json` + `cookie.db` + `comic_source/*` 打成一个 zip（`.venera` 后缀）上传/下载。

**服务端只要实现 WebDAV 端点，App 侧零改动就能同步**。这是整个需求里性价比最高的一环。

### ✅ 结论 3：阅读器 "NAS 优先" 改动量很小

阅读器现在的分支是（`lib/pages/reader/images.dart:41`）：

```dart
if (本地已下载) { 读本地文件 } else { 走网络图片 }
```

只需要在"走网络"分支之前插一层"问 NAS 有没有缓存"，以及让 `ReaderImageProvider` 支持带鉴权头的 HTTP。**不需要**改数据库、不需要伪装成"已下载"。

### 🔓 结论 4（坑）：`sourceKey.hashCode` 必须精确复现

收藏夹和历史表里的 `type` 字段**不是字符串 `"jm"`，而是 Dart 的 `"jm".hashCode`**（如 `769844263`）。服务端算不出来就永远匹配不上 App 数据。

我已经破解并验证了算法（14 个源全部对上）：

```python
h = 0
for ch in s:
    h = (h + ord(ch)) & 0xFFFFFFFF
    h = (h + (h << 10)) & 0xFFFFFFFF
    h ^= h >> 6
h = (h + (h << 3)) & 0xFFFFFFFF; h ^= h >> 11
h = (h + (h << 15)) & 0xFFFFFFFF
return h & 0x3FFFFFFF      # 30 位
```

> 因为这是"依赖实现细节"，我建议服务端**同时**维护一张 `sourceKey → int` 持久映射表（首次由 App 上报），不要长期依赖算法。

## 三、方案架构

```
┌──────────────────┐          ┌──────────────────────────────────────┐
│   Venera App     │          │        NAS (Docker 单容器)            │
│                  │          │                                      │
│  DataSync ───────┼── WebDAV ─▶  /webdav     ← 零改动接住现有同步   │
│                  │          │      │                               │
│  NasClient ──────┼── HTTP ──▶  /api/v1/ping       探活             │
│                  │          │  /api/v1/cached   查缓存            │
│                  │          │  /api/v1/download 入队              │
│  阅读器 ◀────────┼── HTTP ──▶  /api/v1/img/<key>  图片直出         │
│                  │          │                                      │
│  管理页(可选) ────┼─────────▶  /              （内嵌静态页）        │
└──────────────────┘          │                                      │
                              │  sync/   解包·合并·导出 .venera      │
                              │  source/ goja 宿主 + 35 个源         │
                              │  job/    任务队列 + worker 池        │
                              │  store/  文件卷（可换 S3/MinIO）     │
                              └──────────────────────────────────────┘
```

### 数据流（三条主线）

**A. 同步流**
```
App 改动 → saveData() → DataSync.uploadData() → PUT /webdav/xxx.venera
                                                        │
NAS: 解包 → 解析 local_favorite.db / comic_source/*.data / cookie.db
    → 写入 NAS 的 SQLite（收藏、账号、Cookie）
    → 生成"待下载"任务
```

**B. 下载流**
```
job worker 从队列取任务
  → goja 加载源 → loadInfo(comicId) 拿章节
  → loadEp(comicId, ep) 拿图片 URL 列表
  → getImageLoadingConfig(url, cid, eid) 拿 headers/解密逻辑
  → 下载 → (可选 modifyImage) → 按 App 布局落盘
       <store>/<漫画目录>/cover.jpg
       <store>/<漫画目录>/<章节目录>/0.jpg 1.jpg ...
```

**C. 阅读流**
```
App 打开章节 → 问 /api/v1/cached?source=jm&cid=xxx&ep=yyy
   ├─ 命中 → 拿 /api/v1/img/... 列表 → ReaderImageProvider 直接加载
   └─ 未命中 → 走原有网络逻辑（并在后台触发 NAS 下载，可选）
```

## 四、技术栈推荐

### 服务端（推荐方案）

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **Go 1.22+** | 单二进制、交叉编译 x86/ARM、goroutine 适合大批量并发下载、镜像可 < 30 MB |
| JS 引擎 | **goja**（纯 Go） | 实测 35/35 源通过、零 CGO、部署简单 |
| HTTP | **`net/http` + chi** | 轻量 |
| 元数据 | **SQLite（modernc.org/sqlite，纯 Go）** | 单文件零运维，语义与 App 侧一致 |
| 图片存储 | **本地卷（默认）**，抽象 `Storage` 接口 | NAS 场景最自然，可后接 S3/MinIO |
| 任务队列 | **SQLite 表 + worker 池** | 不额外引入 Redis 容器 |
| 日志 | `slog`(JSON) | 标准库 |
| 鉴权 | Bearer Token | 自用场景越简单越好 |

**镜像**：多阶段构建 → `alpine` 或 `distroless`，多架构 `linux/amd64,linux/arm64`。

### App 端（保持 Flutter 现有栈）

| 改动 | 位置 |
|---|---|
| NAS 设置页 | `lib/pages/settings/app.dart` 新增 `_NasSetting` |
| 同步（feature flag） | 新增 `lib/utils/nas_sync.dart` |
| 阅读器 NAS 优先 | `lib/pages/reader/images.dart:41` + `reader_image.dart` |
| 下载按钮 | `lib/pages/comic_details_page/actions.dart:134` 旁 |

### 明确不推荐的路线

| 路线 | 为什么不行 |
|---|---|
| ❌ Flutter 编译成 Linux 桌面塞进容器 | 需要 GTK + X11 + WebKit，镜像 500 MB+，还要虚拟显示；纯浪费 |
| ❌ 服务端写 `local.db` 伪装成"App 已下载" | `directory` 路径语义、`downloadedChapters` 状态会互相污染，且 App 看不到真实文件 |
| ❌ Docker 里塞 Chromium 过 Cloudflare | 镜像爆炸、维护地狱；用"Cookie 复用"替代 |
| ❌ 用 Node.js / Python | 前者内存与镜像大，后者 GIL 限制并发下载 |
| ❌ 用 Dart 写服务端"复用源码" | `flutter_qjs` 强依赖 Flutter 引擎，脱离后需自写 quickjs FFI，工程量比 Go 方案大 |

## 五、分阶段计划

### Phase 0 · 验证（约 1 周）— 建议先做
- Go PoC：3 个目标源跑通 `loadInfo → loadEp → 下载图片 → 落盘`
- 解析真实 `.venera` 同步包，验证 `local_favorite.db` 可读
- 验证 `onResponse`（解密）/ `modifyImage`（JM 切片）两条特殊路径
- **产出**：「哪些源可用」清单 + 可行性报告

### Phase 1 · 服务端 MVP（2–3 周）
- WebDAV 兼容端点（接住现有 `DataSync`）
- SyncKit：解包 / 合并 / 导出
- SourceKit：goja 宿主
- 任务队列 + worker 池 + 重试
- 下载落盘（复用 App 目录布局）
- Docker 镜像 + compose

### Phase 2 · App 改造（约 2 周）
- NAS 设置页 + 探活
- 在线自动同步（feature flag）
- 阅读器 NAS 优先
- 详情页"下载到 NAS"按钮 + 进度

### Phase 3 · 增强（持续）
- 增量同步协议（多设备冲突合并）
- 管理 Web UI
- 收藏夹自动追更
- 加密同步包

## 六、需要你决策的 7 个问题

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | **同步协议** | A. W1 只做 WebDAV（零改 App，纯备份）<br>B. W2 自定义 HTTP（增量/合并/反向指令） | **A 先上线，B 做增强**。W1 几乎白送，W2 才是完整体验 |
| 2 | **收藏来源** | A. 只读同步包里的本地收藏夹<br>B. 也接网络收藏（需账号 Cookie） | **先 A 后 B**。A 零配置即可覆盖大多数用户 |
| 3 | **JS 引擎** | A. goja（纯 Go）<br>B. quickjs（CGO，与 App 100% 一致） | **goja**。实测够用；留 quickjs 作为升级路径 |
| 4 | **App 可否改造** | 允许 / 不允许 | 若不允许，R3/R4 体验会差很多，建议**允许**（改动集中在 4 个文件） |
| 5 | **图片存储** | A. 本地卷<br>B. MinIO / S3 | **本地卷**，接口抽象好，后续可换 |
| 6 | **目标架构** | amd64 / arm64 / 都要 | 建议**都要**（多阶段交叉编译成本很低） |
| 7 | **管理界面** | A. 纯 API + 日志<br>B. 内嵌 Web UI | **先 A 后 B**，Phase 3 再补 |

## 七、风险提示（务必知悉）

| 风险 | 说明 |
|---|---|
| **源可用性不稳定** | 站点改版、加 Cloudflare 都会让源失效；建议锁定 `venera-configs` 版本并按源隔离失败 |
| **Cloudflare / 登录墙** | 部分源需要真实浏览器。**缓解**：复用同步包里的 `cookie.db`（含 `cf_clearance`）与 `ua`，仍失败则降级只在 App 端下载 |
| **JM 类源需要图片变换** | `modifyImage` 会把长图切片重排；服务端需实现等价逻辑（可单独写 Go 版，比跑 JS 更快） |
| **`hashCode` 依赖实现细节** | 已破解，但建议落成映射表，避免未来 Dart 变更导致静默错配 |
| **凭据安全** | 同步包含明文 Cookie。服务端**必须**强制 HTTPS，建议后续做包级 AES-GCM |
| **存储膨胀** | 需要配额 + LRU + 只保留收藏夹内容的策略 |
| **合规** | 仅个人自用、不对外提供服务 |
