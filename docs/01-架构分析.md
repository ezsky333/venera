# Venera NAS 服务端改造 — 架构分析

> 分析对象：`venera-app/venera` @ `a0eba91`（v1.6.3，2026-04-05），`venera-app/venera-configs` @ main（35 个可用源脚本）
> 本地路径：`D:\MyProject\venera\venera`、`D:\MyProject\venera\venera-configs`

---

## 1. 结论先行（TL;DR）

| 问题 | 结论 |
|---|---|
| 服务端能不能跑漫画源？ | **能**。已实测：`init.js` + 35/35 个源脚本在 Go 的 `goja` 引擎中全部加载成功，并端到端跑通 `loadInfo` → `loadEp` 的网络调用链。**不需要 Flutter 运行环境**。 |
| 同步怎么做？ | 现有 WebDAV 同步协议**已够用**（一个 `.venera` zip），服务端实现 WebDAV 挂载即可"自动同步"，但要改协议解决冲突与下载指令回传。 |
| 收藏从哪来？ | 两条路：① 读同步包里的 `local_favorite.db`（本地收藏夹）；② 服务端自己调源的 `favorites.loadComics`（网络收藏，需账号 Cookie）。**推荐两者都做**，前者零配置，后者能力完整。 |
| 阅读能否优先 NAS？ | 能，且改动小。阅读器走 `LocalManager().isDownloaded()` 分支时读本地文件；只需在 `ReaderImageProvider` 与 `_ReaderImagesState.load()` 前插入一层"NAS 缓存探测"。 |
| 最大风险 | ① `sourceKey.hashCode` 是 **Dart 私有哈希**，服务端必须复现（已破解算法，见 §5.3）；② 部分源需要 JS 图片变换（JM 切片）和 Cloudflare 挑战（要 WebView）；③ 源的 `settings` 依赖真实 App 内交互。 |
| 推荐技术栈 | **Go + goja + SQLite + MinIO/文件系统 + 单二进制 Docker**；App 侧保持 Flutter，只加一个"NAS 客户端"薄层。理由见 §7。 |

### 2.1 漫画源机制（最关键）

源 = 一个 JS 文件，声明一个 `class Xxx extends ComicSource`，导出结构化契约：

```js
class Example extends ComicSource {
  name = "示例"; key = "example"; version = "1.0.0";
  account = { login, logout, ... }        // 可选：账号
  favorites = { loadComics, loadNext, loadFolders, addOrDelFavorite, ... }
  explore / category / categoryComics / search   // 可选：发现页
  comic = {
    loadInfo: async (id) => ComicDetails,
    loadEp:   async (id, ep) => ({ images: string[] }),
    loadComments / sendComment / ...      // 可选
  }
  settings = { ... }                       // 需要用户填的配置
}
```

宿主（App）通过 `sendMessage({method, ...})` 回调提供能力，`assets/init.js`（40 KB）是**纯 JS 桥**，把 `sendMessage` 包装成 `Network.*`、`Convert.*`、`HtmlDocument`、`fetch`、`UI.*` 等 API。

**实测用到的 host API 分布（35 个源，共 1200+ 调用点）：**

| API | 次数 | 说明 |
|---|---|---|
| `Network.get` | 210 | 必需 |
| `Network.post` | 66 | 必需 |
| `new HtmlDocument` | 89 | 必需（需 DOM 解析） |
| `Convert.*` | 60 | 必需（md5/sha/aes/rsa/base64/gbk/utf8） |
| `console.*` | 57 | 建议实现 |
| `fetch(...)` | 19 | 必需（init.js 里的封装） |
| `Network.delete` | 19 | 必需 |
| `Network.deleteCookies` / `setCookies` | 16 / 10 | 需要 Cookie 持久化 |
| `UI.*` | 27 | **服务端可 stub 为 no-op**（登录交互无法自动化） |
| `APP.locale` / `APP.version` | 7 | 必填常量 |
| `compute()` | 2 | 可选（Worker 池） |

> **结论**：host API 只需要实现约 12 个方法，其余可以返回空/stub。这让"在容器里跑源"成为一个**可控工程量**，而不是无底洞。

### 2.2 数据模型（决定 NAS 侧表结构）

| 实体 | 存储位置 | 主键/关键字段 |
|---|---|---|
| 已下载漫画 | `local.db` 单表 `comics` | `(id, comic_type)`，含 `directory`、`chapters`(JSON)、`downloadedChapters`(JSON) |
| 本地收藏夹 | `local_favorite.db`，**每个收藏夹一张表** + `folder_order` + `folder_sync` | 表内 `(id, type)`，`type` 是 **`sourceKey.hashCode`** |
| 阅读历史 | `history.db` 单表 `history` | `id` 主键，`type` 同上，`ep/page/group/readEpisode` |
| 源账号/Cookie | `comic_source/<key>.data`(JSON) + `cookie.db` | 按源隔离 |
| 配置 | `appdata.json`（含 `webdav`、各源 settings） | 键值 |

**图片文件布局（本地下载）**：
```
<localPath>/<漫画目录名>/
    cover.jpg
    <章节目录名>/0.jpg, 1.jpg, 2.jpg ...     # 按索引命名
```
`LocalManager.getImages()` 按文件名数字前缀排序，`cover.` 开头跳过。**这个布局可以直接复用到 NAS，让 App 零改造成"读本地"**。

### 2.3 现有同步链路（重要发现）

`DataSync` 就是一个 **WebDAV 客户端**，行为非常简单：

- **上传**：把 `history.db` + `local_favorite.db` + `appdata.json` + `cookie.db` + `comic_source/*` 打成 **一个 zip**，命名 `<天数>-<dataVersion>.venera`，写进 WebDAV 根目录；保留最近 10 个。
- **下载**：取目录里文件名最大的 `.venera`，比 `dataVersion` 大就解压覆盖。
- **触发**：`appdata.saveData()` / 源 `saveData()` / 阅读器 `dispose()` 都会 `uploadData()`；启动时 `downloadData()`。

**这意味着**：只要服务端提供一个 WebDAV 端点，App 侧**一行不改**就能把账号、收藏、历史同步上来。这是整个需求里性价比最高的一环。

**但现有协议的缺陷**：
1. **整包覆盖、无合并** —— 多设备并发会互相覆盖（`dataVersion` 是单调整数，天生冲突）。
2. **不能反向下发** —— NAS 端无法告诉 App "这个漫画已缓存"，也无法让 App 触发 NAS 下载。
3. **`cookie.db` 明文上传** —— 账号安全靠 WebDAV 的 Basic Auth，需要额外加密。

## 3. 需求拆解与可行性判断

### R1 — "探测到 NAS 在线 → 自动同步账号配置/收藏"

| 子问题 | 判断 |
|---|---|
| 探测 | 简单。客户端定时 `GET /api/v1/ping`，带指数退避；或复用 WebDAV `PROPFIND`。 |
| 自动同步 | 现成的 `DataSync` 已实现。需增加：**在线检测 → 立即 pull/push**，离线时排队（`dataVersion` 递增 + 待同步标记）。 |
| 冲突 | 现有 `dataVersion` 单调整数不足以做并发合并。**建议服务端维护版本向量/逻辑时钟**，或退化为"字段级 last-write-wins + 收藏夹集合求并集"（收藏语义天然是集合，可安全合并）。 |

### R2 — "服务端自动下载收藏夹全部内容"

| 子问题 | 判断 |
|---|---|
| 收藏从哪来 | ① 解析同步包 `local_favorite.db`（零配置，**首选**）；② 调源 `favorites.loadComics` 拉网络收藏（需 Cookie；多文件夹需 `loadFolders`）。 |
| 能否下载 | **能**，已验证 `loadInfo` → `loadEp` → 图片 URL 链可跑通。图片下载需要走源的 `getImageLoadingConfig(url, cid, eid)`，其中可能含 headers/加解密。 |
| 难点 | ① **JM 类源需要 JS 图片变换**（`modifyImage` 把长图切成 N 段后重排）——服务端需实现等价变换；实测 35 个源里只有 `jm.js` 用 `modifyImage`，`ccc.js`/`comic_walker.js` 用 `onResponse` 解密。② 部分源有 Cloudflare 挑战，需要真实浏览器指纹（见 §6 风险）。 |
| 存储 | 保持 §2.2 的目录布局 + `0.jpg` 数字命名，App 端可直接当"已下载"。 |

### R3 — "App 阅读时若 NAS 已缓存则优先从 NAS 读"

现状代码（`lib/pages/reader/images.dart:41`）：

```dart
if (reader.type == ComicType.local ||
    LocalManager().isDownloaded(cid, type, chapter, chapters)) {
    // 走本地文件
} else {
    // 走 loadComicPages() → 网络图片
}
```

改造点非常集中，只需两处：
1. `_ReaderImagesState.load()`：在判断为网络路径时，先问 NAS "这章有没有缓存"，有就拿 `GET /api/v1/img/<...>` 的 URL 列表。
2. `ReaderImageProvider.load()`：支持 `http(s)://` 走 NAS 域名 + 鉴权头（现在只区分 `file://` 与网络）。

**关键收益**：不需要伪装成本地下载（不用改 `local.db`），NAS 缓存与本地缓存**共存**，用户可以随时清理本地。

### R4 — "App 里按钮主动触发下载到 NAS"

现状 `download()`（`lib/pages/comic_details_page/actions.dart:134`）只支持 `LocalManager().addTask(...)` 写本地。改造：
- 详情页/章节菜单增加 "Download to NAS" 入口；
- 调 `POST /api/v1/download`，body 带 `{sourceKey, comicId, chapters?}`；
- 服务端入队 → 前端轮询/WebSocket 推进度。

## 5. 关键技术难点（含已验证结论）

### 5.1 【已解决】漫画源能否脱离 Flutter 运行

**实测**（Go 1.26 + `github.com/dop251/goja`）：

```
init.js 加载：OK
35 个源脚本：OK=35 FAIL=0
ES6+ 支持：async/await、optional chaining、nullish、class fields、
          generator、for-of 解构、命名分组正则 → 全部 OK
MangaDex 端到端：loadInfo 返回真实标题「我独自升级」 → OK
```

**注意**：goja **不提供** `TextDecoder` / `atob` / `Intl` / `Worker` / `setTimeout`。我扫过 35 个源，这些 API **实际使用量为 0**（`Buffer` 的 64 次命中全是 `Uint8Array.buffer`，不是 Node 的 `Buffer`）。但需要在宿主侧补 `setTimeout`（App 的 `init.js` 里 `setTimeout` 依赖 `sendMessage({method:'delay'})`，服务端实现成 goroutine 定时器即可）。

> **备选**：如果将来某些源用到 V8 特性，可换成 `github.com/robertkrimen/otto`（更旧的 ES5）——不行；应升级为 **`quickjs` CGO 绑定**（和 App 使用同一个引擎，行为 100% 一致）。这是"最终正确性"选项，代价是 CGO 构建。

### 5.2 【需工程】图片加载配置与解密

App 的图片加载不是简单 GET：

```dart
configs = await comicSource.getImageLoadingConfig(imageKey, cid, eid)
// 可能返回 { url, method, data, headers, onResponse, modifyImage, onLoadFailed }
```

- `onResponse`：字节级变换（异或/解密），可在 goja 里执行；
- `modifyImage`：**图片级**变换（JM 的切片重排），需要图像解码 → JS `Image` 对象 → 编码。App 用 `lodepng` + Flutter `ui.instantiateImageCodec`。服务端可选：Go 的 `image/png` + 一个 JS `Image` 门面（只支持 png），或对 JM 单独写 Go 版切片逻辑（更简单、更快）。

### 5.3 【已破解，必须做对】`sourceKey.hashCode`

收藏、历史、本地库里的 `type` 字段**不是字符串**，而是 `sourceKey.hashCode`（Dart `String.hashCode` 的 30 位结果）。服务端如果算不对，就**永远匹配不上 App 的数据**。

已实测复现（14 个测试向量全部命中）：

```python
def dart_string_hash(s: str) -> int:
    h = 0
    for ch in s:
        h = (h + ord(ch)) & 0xFFFFFFFF          # UTF-16 code unit
        h = (h + (h << 10)) & 0xFFFFFFFF
        h ^= h >> 6
    h = (h + (h << 3)) & 0xFFFFFFFF
    h ^= h >> 11
    h = (h + (h << 15)) & 0xFFFFFFFF
    return h & 0x3FFFFFFF                        # 30 位掩码
```

验证：`jm → 769844263`、`ehentai → 385625716`、`picacg → 553570794`、`Komiic → 637999886` … 全部与 `dart run` 输出一致。

> ⚠️ 这是**实现细节依赖**：Dart 未来若改算法，App/服务端会静默不匹配。**建议**：同时在服务端维护 `sourceKey → int` 的持久化映射表，首次由 App 上报，之后只查表。

### 5.4 【需设计】同步协议升级

现有 `.venera` 整包覆盖在多设备下必然冲突。建议 **双协议并存**：

- **W1（零改动）**：服务端实现 WebDAV，App 原样使用。适合"单设备 + NAS 只做备份"。
- **W2（推荐）**：新 HTTP API，服务端提供**结构化增量**：
  - `GET /api/v1/sync/manifest` → 各实体版本号
  - `POST /api/v1/sync/push` `{favorites: {add:[], remove:[]}, history: [...]}` → 服务端做**集合合并**（收藏 = 并集；历史 = 按 `(id,type)` last-write-wins）
  - `GET /api/v1/sync/pull?since=<cursor>` → 增量下发

App 侧 `DataSync` 保留作为兜底，新增 `NasSync` 实现 W2。

### 5.5 【需确认】账号登录

源的 `account.login(username, password)` 可以纯 JS 调通（发请求、拿 token、`saveData`）。但部分源（`ehentai`、`nhentai`、`manga_dex`、`ccc`、`mycomic`）提供 `loginWithWebview` —— 需要真实浏览器。

**方案**：服务端优先走 `login()`；失败时提示用户在 App 内登录后，把 `comic_source/<key>.data` 和 `cookie.db` 一起同步上来（现有同步包**已经包含**这两个文件，天然可用）。这避免了在容器里塞 Chromium。

### 5.6 【需确认】Cloudflare

App 端遇到 CF 挑战会弹 WebView 让用户过验证。服务端无法交互。**缓解**：
- 优先使用不触发 CF 的源；
- 同步包里的 `cookie.db` 若含 `cf_clearance` + `ua`，服务端可直接复用（App 正是把 `ua` 存在 `implicitData` 里）；
- 仍失败则该源降级为"只在 App 端下载"。

## 6. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| `hashCode` 算法变更 | 数据全部错配 | 服务端持久化映射表，不依赖算法 |
| 源脚本更新破坏兼容 | 下载失败 | 锁定 `venera-configs` 版本；解析失败只影响单源 |
| Cloudflare / 登录墙 | 部分源不可用 | Cookie 复用 + 优雅降级 |
| 站点反爬（限速/封 IP） | 下载大量失败 | 全局令牌桶、单站点并发=1~2、失败退避 |
| 版权/合规 | 法律风险 | 仅个人自用、不对外提供服务；README 明示 |
| 存储膨胀 | 磁盘满 | 配额 + LRU + 保留策略（只保留收藏夹内容） |
| 同步包含明文 Cookie | 凭据泄露 | 服务端强制 HTTPS + 可选 AES-GCM 加密包 |
| App 改动引入回归 | 现有用户受影响 | 所有改动 feature-flag 包裹，默认关闭 |

## 7. 技术栈推荐（含取舍）

### 7.1 服务端

| 层 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| 语言 | **Go 1.22+** | Rust / Node / Dart | 单二进制、交叉编译到 amd64/arm64（NAS 主流架构）、goroutine 天然适配"大量并发下载"、Docker 镜像可 < 30 MB |
| JS 引擎 | **goja** | quickjs(CGO) / otto | 纯 Go、零 CGO、实测 35/35 源通过；quickjs 作为"高保真"升级路径 |
| HTTP | **标准库 `net/http` + chi** | gin / echo | 依赖少；chi 提供中间件与路由 |
| 存储元数据 | **SQLite (modernc.org/sqlite, 纯 Go)** | PostgreSQL | 单文件、零运维，与 App 的 SQLite 语义一致；避免 CGO |
| 图片存储 | **本地卷（默认）** | MinIO / S3 | NAS 场景本地卷最自然；抽象 `Storage` 接口后可切 S3 |
| 队列/任务 | **内置（SQLite 表 + worker 池）** | Redis / NATS | 不引入额外容器；单机足够 |
| 日志 | `slog` (JSON) | zap | 标准库，够用 |
| 配置 | env + `config.yaml` | viper | 简单 |
| 鉴权 | **Bearer Token / API Key** | JWT | 自用场景，越简单越好 |
| 前端（管理页） | 可选：**嵌入式静态页**（SvelteKit/Vue 构建后 embed） | 无 | 先做 API，UI 可后补 |

**镜像建议**：`golang:1.23-alpine` 多阶段 → `gcr.io/distroless/static` 或 `alpine:3.20`，最终 ~25 MB。多架构 `linux/amd64,linux/arm64`（群晖/威联通多为 x86，部分 ARM）。

### 7.2 App 端（Flutter，保持现有栈）

| 改动 | 位置 | 说明 |
|---|---|---|
| NAS 探测 + 设置页 | `lib/pages/settings/app.dart`（新增 `_NasSetting`） | 复用 WebDAV 设置页形态 |
| 同步 | `lib/utils/data_sync.dart` 旁新增 `nas_sync.dart` | 不改原逻辑，feature flag |
| NAS 缓存查询 | `lib/pages/reader/images.dart` + 新增 `nas_client.dart` | 只加分支 |
| 图片源 | `lib/foundation/image_provider/reader_image.dart` | 加 `nas://` 或 `http` + header 支持 |
| 下载按钮 | `lib/pages/comic_details_page/actions.dart` | 菜单项 + API 调用 |

**不建议**的路线：
- ❌ 不要 fork 成"NAS 专用版"——失去上游更新；
- ❌ 不要用 `flutter build linux` 做成桌面容器——要 GTK+X11、镜像 500 MB+、还要装 WebKit，完全不划算；
- ❌ 不要让服务端假装成"本地下载"写 `local.db`——`directory` 路径语义、`downloadedChapters` 状态会互相污染。

### 7.3 为什么不是其他语言（对照）

| 方案 | 评价 |
|---|---|
| **Dart 服务端**（复用 `comic_source` 代码） | 理论最优（100% 行为一致），但 `flutter_qjs` 依赖 Flutter 引擎，脱离 Flutter 无法用；需替换成 `dart:ffi` 直连 quickjs，工程量大且生态弱。**放弃**。 |
| **Node.js**（`quickjs-emscripten` / `vm`） | JS 兼容性最好，但 Node `vm` 不支持跨线程隔离、内存占用高、镜像 150 MB+。可作 PoC，不作长期方案。 |
| **Rust**（`rquickjs`） | 性能最好、单二进制，但开发效率低于 Go，且团队熟悉度通常更低。 |
| **Python**（`quickjs` 包） | GIL 会严重限制并发下载；部署体积大。**不推荐**。 |
